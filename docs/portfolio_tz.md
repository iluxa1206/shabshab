# ТЗ: модуль ПОРТФЕЛЬ (конструктор набора флоатеров)

Статус: согласовано 2026-08-27. Ветка `floaters-desk-deploy`.

## 1. Задача

По фильтрам (рейтинг, срок, эмитент, база купона, ОФЗ/корп, ликвидность) и
сумме собрать портфель из `n` флоатеров: максимум спреда при ограничениях
диверсификации и реальной глубины стакана. Набор правится руками и считается
как портфель — доход, риск, календарь выплат, концентрация.

Выдача разовая (stateless): запрос → набор → таблица. В БД ничего не пишем.
Портфельный слой уже сносили 2026-07-28 (память `funds-module-removed`) —
хранилище не воскрешаем, пока конструктор не докажет пользу.

## 2. Решения, зафиксированные с заказчиком

| Вопрос | Решение |
|---|---|
| Цель отбора | максимум спреда при ограничениях; плюс режим «лесенка по срокам» |
| Веса | равные деньги + кап по стакану, остаток перераспределяется |
| Универс | только флоатеры (фиксы и g-спред — не в этой итерации) |
| Хранение | stateless, без таблиц БД |
| Общий код | **работающие СИГНАЛЫ не трогаем**: ни `screener_core`, ни `SignalsModule.jsx` |

Следствие запрета на правку ядра: ценообразование позиции (VWAP по лестнице +
Y-IDX к нему) пишется в `portfolio_build` заново поверх публичных хелперов
`screener_core` (`vwap_for`, `money_upto`, `exact_y_idx`, `y_idx_at`,
`side_money_rub`). Осознанный дубль ~40 строк; страховка от расхождения цифр —
антидрейф-тест §9.7.

  "no_call": false,                // выкинуть с известным коллом/офертой в сроке

  "spread_min": null, "spread_max": null,   // Y-IDX бп — отсечка мусора

  // ── сборка ──

  "buckets": [1, 2, 3],            // границы корзин лесенки, лет; only mode=ladder

  "max_per_emitter": 1,            // бумаг на эмитента

## 4. Алгоритм (`services/portfolio_build.py`)

```python
def normalize(raw) -> dict
def build(params, uni, metrics, depth_map, adv, calendar, today=None) -> dict
async def build_live(raw) -> dict     # снимок рынка + adv + календарь → build
```

`build` — чистая функция без сети: всё, что ходит наружу, собирает
`build_live` (`screener_core.market_snapshot()`, `bars.adv_map(30)`,
`payments_calendar.build_payments_calendar()`). Так тесты обходятся фикстурами.

**Шаг 1. Отбор.** `screener_core.static_candidates(params, uni, today)` как есть —
свой фильтр по рейтингу/сроку/суборду НЕ пишем (тест §9.5). Поверх — то, чего в
ядре нет: `bases`, `no_amort` (`has_amort` из строки метрик), `no_call`
(`has_call` реестра или `offer_date` строки метрик), `min_adv_rub` (`adv_map`).
`exclude` вычитается тут же. `pin` добавляется, даже если бумага фильтру не
соответствует — человек знает, что делает; в строке остаётся флаг `pinned`.

**Шаг 2. Цена** (`_priced`), тикет = `amount_rub / n`:
- нет метрик / `price_stale` / `implausible` / `price_thin` / нет `ask` → `rejected`;
- `face = row["face_px"] or 1000`, `accrued = row["accrued_settle"] or 0`;
- `v = vwap_for(ladder_ask, ticket, face, accrued)`; `None` → `rejected(no_depth)`;
- `v["partial"]` → бумагу **оставляем**, `capped=True`, доступные деньги
  `v["money"]` (скринер такую выбрасывает через `vwap_passes` — портфелю она
  годится, просто меньшей позицией);
- `y_idx = exact_y_idx(isin, v["px"])`, откат `y_idx_at(row, v["px"], "ask")`;
  нет числа — бумага годится, только если границы спреда не заданы;
- отсечка `spread_min/max` → `rejected(spread_out)`.

**Шаг 3. Набор** (`_pick`), сортировка по `y_idx` вниз:
- сначала `manual` и `pin`, затем жадно сверху;
- кэпы проверяются на каждом взятии: `max_per_emitter` (штуки),
  `max_emitter_share` и `max_rating_share` (деньги, считаются от `amount_rub`
  по плановому тикету);
- `mode="spread"` — один общий проход до `n`;
- `mode="ladder"` — корзины из `buckets` (умолчание `[1,2,3]` → 0-1, 1-2, 2-3,
  3+ лет). Квота = `n // число корзин`, остаток отдаётся корзинам с бо́льшим
  числом кандидатов. Внутри корзины — тот же жадный проход. Пустая или
  недобранная корзина → квота уходит соседям + предупреждение;
- меньше `n` — предупреждение; кэпы **не ослабляем молча**.

**Шаг 4. Размер** (`_size`):
- `manual`-позиции берут ровно запрошенное; остаток `amount_rub − Σ manual`
  делится поровну между остальными;
- урезка до `v["money"]` там, где стакан тоньше тикета (`capped=True`);
- высвободившееся одним вторым проходом раскидывается по неурезанным. Запас
  считается по ЁМКОСТИ ВСЕЙ СТОРОНЫ книги (`side_money_rub`), а не по набору на
  тикет: `money_avail` из `vwap_for` равен запрошенному, и по нему запаса не
  видно вовсе. Один проход, без итераций до сходимости — недобор честно
  показывается, а не размазывается алгоритмом;
- позиция, получившая добавку, ПЕРЕОЦЕНИВАЕТСЯ на фактический размер: добавка
  съедает уровни глубже набранных, и без пересчёта в таблице стоял бы спред
  верха книги при покупке половины стакана;
- `manual` больше стакана исполняется как просили, но с `price_estimated=true`
  (цена — VWAP всей книги) и предупреждением;
- лоты: `qty = floor(money / (face*price/100 + accrued))`, `money_rub`
  пересчитывается по факту; `qty == 0` → `rejected(zero_lot)`;
- недобор → `totals.shortfall_rub` + предупреждение.

**Шаг 5. Агрегаты** (`_totals`) и **календарь** (`_calendar`) — §5.

Цена позиции — **средневзвешенная по набору**, не верх стакана, и Y-IDX
пересчитан к ней: иначе цифра относится к 50 бумагам сверху книги, а покупаться
будет вся лестница.

## 5. Аналитика набора

Веса везде денежные: `w_i = money_rub_i / Σ money_rub`.

| Метрика | Формула | Источник |
|---|---|---|
| `y_idx_w` | `Σ w_i · y_idx_i` | шаг 2 |
| `dur_w` | `Σ w_i · spread_dur_i` | `row["spread_dur"]` |
| `pnl_100bp_rub` | `Σ money_i · spread_dur_i / 100` | оно же |
| `current_coupon_w` | `Σ w_i · current_coupon_i` | `row["current_coupon"]` |
| `coupon_12m_rub` | Σ COUPON-событий на 365 дней вперёд × `qty` | календарь |
| `rating_avg` | среднее по денежным весам на шкале AAA=1…B=6, наружу буквой | реестр |
| `by_base/by_rating/by_bucket` | доли денег | — |
| `top_emitters` | топ-5 по деньгам | — |
| `hhi_emitter` | `Σ (доля эмитента)²` | — |
| `adv_days` (в строке) | `money_rub / adv_rub` | `bars.adv_map(30)` |

**Календарь** — из `payments_calendar.build_payments_calendar()` (кэш на день,
весь универс): берём события наших ISIN, умножаем `amount_rub` события на `qty`,
группируем по месяцам на 24 месяца вперёд. Своей математики потоков не пишем.

## 6. UI (`PortfolioModule.jsx`)

- **Форма**: чипы рейтингов, пикеры эмитента и ISIN (дёргают существующие
  `/api/signals/emitters` и `/api/signals/search`), срок «от/до», ОФЗ/корп,
  база купона, тумблеры «без амортизации» / «без колла» / «скрыть суборды»,
  мин. оборот, границы Y-IDX, `n`, сумма, кэпы, переключатель
  «Спред | Лесенка».
- **Таблица позиций**: ISIN/имя, эмитент, рейтинг, формула купона, срок, цена,
  Y-IDX, лоты, сумма, доля, дюрация, оборот-дней; значки `capped`,
  `pinned`, `manual`, `price_estimated`; в строке — поле ручной суммы,
  крестик «убрать» (→ `exclude`), клик по имени → карточка бумаги (`?isin=`).
- **Плитки**: сумма и недобор, Y-IDX, дюрация, спред-риск ±100 бп, купонный
  доход 12 мес, текущая купонная доходность, эмитентов, ср. рейтинг.
- **Панели**: концентрация (эмитенты/рейтинги/база/корзины), календарь выплат
  по месяцам, пул замен (кнопка «взять» → `pin`), отсев со счётчиками по
  причинам (сворачиваемый).
- **Прочее**: параметры сборки в URL (вернуться и переслать), кнопка «копировать
  ISIN» (`clipboard.js`), «Пересобрать».

## 8. Чего в этой итерации НЕТ

БД и сохранение портфелей; фиксы и g-спред; оптимизатор целевой дюрации;
переоценка во времени и сравнение с бенчмарком (`benchmarks.py` даёт историю
индексов MOEX — сравнивать нечего, пока нет сохранённой даты покупки; это
функция хранилища); экспорт xlsx; отправка набора в телеграм; сценарии «КС ±200
бп» по будущим купонам; отраслевая диверсификация (признака отрасли в данных
нет).

## 9. Критерии готовности

1. Пустой фильтр, `n=15`, 100 млн → 15 позиций, ≤1 бумаги на эмитента,
   `Σ money_rub ≤ amount_rub`.
2. Тонкий стакан → позиция урезана (`capped`), остаток перераспределён,
   недобор в `warnings` и `totals.shortfall_rub`.
3. Эмитентов меньше `n` → позиций меньше `n`, предупреждение есть, кэп цел.
4. `mode="ladder"`: в каждой непустой корзине своя квота; пустая корзина отдаёт
   квоту соседям и даёт предупреждение.
5. `portfolio_build` не содержит своего отбора по рейтингу/сроку/суборду
   (тест по образцу `test_core_shared_with_tg`).
6. `manual` фиксируется точно; `Σ manual > amount_rub` → 400; `manual` сверх
   стакана → `price_estimated` + предупреждение, позиция не урезана.
7. **Антидрейф**: там, где глубины хватает, `_priced` даёт ту же цену и тот же
   Y-IDX, что `screener_core.evaluate_candidates` с `min_money_rub = тикет`.
8. Календарь и `coupon_12m_rub` — суммы событий × `qty`, без своей математики
   потоков (проверяется на фикстуре календаря).
9. `pytest` целиком зелёный, `npm run build` проходит, бэкенд стартует.
10. Живой прогон: Y-IDX взятых бумаг сходится с колонкой во вкладке ФЛОАТЕРЫ,
    когда набор укладывается в один уровень стакана.

## 10. Известные риски и каветаты

- **Дубль ценообразования** (§2): защита — только тест §9.7. Правишь
  `evaluate_candidates` — смотри этот тест.
- **Глубина** — снимок `services/depth`, устаревает за 15 мин. «Влезает» ≠
  «исполнится», а `adv_days` в строке показывает, сколько дневных оборотов
  весит позиция.
- **`no_call` неполон**: `has_call` приходит из corpbonds, вид оферты MOEX не
  отдаёт (память `offer-markers`). Фильтр убирает известные коллы, не все.
- **Жадность по спреду** тянет наверх суборды и мусор → `hide_subord=true` по
  умолчанию, плюс отсев `implausible` / `price_thin`.
- **Разная свежесть данных в одной таблице**: стакан живой, календарь и ADV —
  дневного кэша. Для купонов и оборотов это допустимо; в UI у календаря стоит
  дата расчёта.
- **Диверсификация** только по эмитенту и рейтингу — отраслей в данных нет.
- **Ср. рейтинг** — среднее по буквенной шкале, а не по вероятности дефолта.
  Это индикатор состава, не кредитная оценка.
