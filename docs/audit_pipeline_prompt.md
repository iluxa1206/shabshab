# Промпт: аудит конвейера расчётов

Скопировать целиком в новый чат Claude Code, открытый в этом проекте.

---

Проведи аудит конвейера расчётов и доставки чисел. Работай **через Workflow**:
пять независимых углов параллельно, затем каждую находку отдельный агент пытается
**опровергнуть** (по умолчанию real=false при сомнении). Ничего не чини без моего
согласия — сначала отчёт.

## Что за система

FastAPI + React монитор рублёвых флоатеров (облигации с плавающим купоном), прод на
assetallocator.ru/desk. Первичная метрика — **Y-IDX** (spread), спред доходности над
индексом; по ней принимают торговые решения, поэтому неверное число хуже отсутствующего.

Ключевые файлы:

- `services/universe_stream.py` (~2400 строк) — событийный движок метрик. Очереди
  `_dirty` (полный пересчёт на смену цены сделки) и `_sides_dirty` (дешёвый пересчёт
  сторон стакана, приоритеты `_SIDES_PRIO_*`), такт `metrics_worker`, кэши
  `_level_memo` / `_yoi_cache` / `_yoi_grid` / `_flow_cache` / `_eval_ctx`.
- `services/valuation.py`, `core/valuation.py` — сам расчёт: PV, XIRR, солверы SM/DM.
- `services/yidx_exact.py` — батч точного Y-IDX по списку цен.
- `services/orderbook_svc.py` — метрики на каждый уровень стакана (лестница).
- `services/accrued.py` — единая лестница источников НКД.
- `api/routes/bonds.py` — `/api/bonds` (полная витрина) и `/api/bonds/quotes`
  (такт 1 с, ответ дельтой по `since`/`epoch`).
- `api/routes/ws.py` + `universe_stream._push_metrics` / `_broadcast_quote` — доставка патчей.
- `frontend-react/src/App.jsx`, `quotesMerge.js`, `tableRows.js` — мердж на фронте.
- `services/heavy.py` — однопоточный исполнитель тяжёлого счёта. GIL держится, поэтому
  батчи режутся **по времени**, а не по количеству.

## Свежий контекст (всё уже в проде)

- Цены сторон в `/api/bonds/quotes` берутся из строки движка, борд-снапшот ISS — фолбэк.
- Спред стороны может браться из сетки цен `_yoi_grid` по свежему верху книги
  (`live_sides`); сетка строится видимым бумагам и при активном фильтре по объёму.
- У котировочного пуша есть метка времени `_ts`, порог живости `LIVE_SIDE_MAX_AGE_SEC`.
- Фронт держит последнее известное число (`y_idx_*_stale`) и показывает его приглушённым,
  пока движок считает; сортировка и фильтр держат строку по последнему значению.
- Прогрев отдаёт движку контексты и потоки (`seed_begin` / `seed_ctx`), засев помечен
  версией и переживает первую сверку версий.

## Исторические грабли — не должны повториться

- **27.08.2026**: спред, посчитанный к прошлой цене, стоял рядом со свежей ценой и
  выглядел согласованным — врал. Правило: цена и спред едут **одной парой** из одного
  расчёта.
- Прочерк честнее правдоподобной прикидки, но пустая клетка не должна висеть, когда
  число уже посчитано и лежит в памяти.
- `docker compose exec ... python -c` поднимает **новый процесс** с пустым `market_cache`:
  всё, что живёт в памяти рабочего процесса, там показывает ноль. Мерить состояние можно
  только по файлам, логам или HTTP с живой сессии.

## Пять углов аудита

1. **Последовательность расчёта.** Путь от события до числа: пуш Alor (`_on_quote`) →
   очереди → такт `metrics_worker` → `_crunch` / `recrunch_sides` → `_fill_side_metrics` →
   `_store_rows`. Какое событие какой пересчёт заказывает, в каком порядке, что имеет
   приоритет. Ищи дыры: события, которые ничего не заказывают; порядок, при котором
   результат зависит от того, что успело раньше; работу, которая делается дважды; бумаги,
   которые могут не попасть в очередь никогда.

2. **Доставка — «всё должно отображаться, как только посчиталось».** Карта путей:
   WS-патч, `/api/bonds/quotes` (с дельтой), `/api/bonds`, мердж на фронте. Для **каждого**
   поля строки (спред по сделке, спреды сторон, спред по средневзвесу, цена и спред набора
   по объёму, дюрация, горизонт) ответь: каким путём доезжает и есть ли состояние, где
   число посчитано на сервере, но на экране его нет или оно устарело. Проверь
   `_quote_delta`: не может ли строка не приехать, если изменилось поле, не входящее в
   сравниваемое содержимое.

3. **Кэш денежных потоков** (`_flow_cache`, `flows_cache` в `valuation._flows`, `flows` в
   `orderbook_svc`). Ключ, значение, кто пишет и читает, когда сбрасывается. **Корректность**:
   не может ли отдаться поток на другой кривой, другом дне, другом НКД, другом графике
   купонов или другой марже. **Полнота**: все ли потребители им пользуются (ищи вызовы
   `calculate_valuation_metrics` без `flows_cache`). **Рост**: чем ограничен, что чистит.

4. **Кэши спредов по ценам уровней стакана.** Их несколько: `_level_memo` (isin, цена),
   `_yoi_cache` (набор цен, TTL), `_yoi_grid` + `yoi_at`, memo подписки в
   `services/alor_ws`, `flows` в `orderbook_svc.build_levels_fn`, `_ctx_cache` в
   `trade_yidx`. Для каждого: ключ, версионирование, инвалидация, потолок. Ищи устаревший
   ответ на новой кривой или после правки справочника, дублирование работы между кэшами,
   кэш, который не спасает из-за построения ключа. **Отдельно объясни**, почему `_level_memo`
   даёт 12 % попаданий и почему сетки перестраиваются десятками в минуту при неизменном
   количестве — и стоит ли это чинить.

5. **Методическая согласованность.** Y-IDX считается в нескольких местах: витрина
   (`universe.py` / `universe_stream`), точный путь (`yidx_exact`), лестница стакана
   (`orderbook_svc`), карточка (`bond_details`), as-of движок (`backdate`), калькулятор
   (`custom_bond`), скринер и сигналы (`screener_core`). Проверь, что все используют одну
   методику, один выбор горизонта прайсинга (правило «цена vs цена выкупа»,
   `preferred_horizon`), один НКД (`services/accrued`), одну кривую и одну дату расчёта.
   Есть сторож `services/yidx_sentinel` — проверь, что он сверяет и чего **не** покрывает.

## Формат отчёта

Только подтверждённые находки, отсортированные по серьёзности. На каждую: файл и строка,
в чём дефект, **конкретный сценарий** (вход → неверный или потерянный результат),
предлагаемое лечение. Отдельным коротким списком — что проверено и оказалось в порядке,
и что было отклонено на проверке и почему. Числа приводи с указанием, чем измерены.
